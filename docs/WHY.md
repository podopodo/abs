# Why ACP exists

Large coding tasks fail less often from an inability to write syntax than from loss of project continuity:

- the agent does not find the existing owner;
- a feature is rebuilt under a new name;
- one public entry follows a new rule while a sibling entry follows the old rule;
- persistence, workers, contracts or legacy loading are omitted;
- later sessions cannot recover why a boundary exists;
- documentation grows into a second, stale codebase.

ACP addresses those failures with five original pillars:

1. **SOT attribution** — each rule-bearing duty has one stable owner ID.
2. **Local inherited context** — directories record only local architectural deltas.
3. **Protected paths** — sensitive work uses declared gateways and contracts.
4. **Echo signals** — features and cross-owner joins have executable guards.
5. **Modification first** — search and extend the existing responsibility before creating another.

The CLI moves repetitive discovery and validation out of the model context. The protocol remains small; the binary produces a bounded task capsule and deterministic health report.

ACP does not attempt to store a prose summary of the whole project. Code, contracts, tests and version control remain authoritative. ACP stores only the relationships needed to retrieve them efficiently.
